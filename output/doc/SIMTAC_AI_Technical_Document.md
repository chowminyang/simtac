# SIMTAC AI

## Technical Description

SIMTAC AI | Scenario Builder | Technical Handoff Overview

Technical description for engineering handoff and stakeholder dissemination | Prepared 2026-04-02

SIMTAC AI is a structured scenario-authoring workstation for clinical simulation teams creating SIMTAC-compliant medical and surgical training cases. What you would inherit is not a generic prompt wrapper or a free-form chatbot, but a guided authoring application built around a 15-section simulation worksheet, section-aware AI generation, scenario-flow editing, SimMan capability validation, Singapore-context defaults, medical image generation for appendices, and editable DOCX export for downstream review. The product is designed to help instructors move from a blank worksheet or a short clinical brief to an export-ready simulation package without losing manual control over the final content.

Technically, the application is a Next.js App Router project using React 19, TypeScript, Tailwind CSS 4, and server-side API routes rather than a separate backend service. The main user surface is a single scenario-builder workspace that persists draft state locally in the browser, while server responsibilities are concentrated in a small set of Node.js API routes for AI generation, section fill, image generation, DOCX export, site authentication, and knowledge-library administration. AI orchestration is built on the OpenAI SDK, using the Responses API for structured scenario generation, vector-store file search for retrieval grounding, and image generation/edit endpoints for appendix images. The core interface boundaries in practice are the React authoring client, the Zod-validated scenario schema layer, the Next.js route handlers, and the external OpenAI file/vector/image services.

From a handoff perspective, the repository is already closer to a domain-specific authoring tool than a proof-of-concept. It includes schema-driven validation, simulator-aware content guardrails, local draft persistence, password-gated site access, passcode-protected knowledge administration, route-level rate limiting, safe error redaction for Singapore identifiers and contact details, reference ingestion scripts, unit and integration tests, and Playwright coverage for key end-user flows. At the same time, the project deliberately avoids heavier infrastructure such as a relational database, user account model, or persistent analytics pipeline, which keeps deployment simple but also defines the main scaling and governance constraints future maintainers would need to address.

## Application Architecture Summary (Text-Only)

The frontend is centered on `src/components/scenario-builder-app.tsx`, which acts as the primary authoring shell for the entire worksheet experience. Users can start in one of two modes: `Create with AI`, which generates a full scenario from a prompt, or `Fill Worksheet`, which completes a partially authored scenario while preserving existing content. The interface supports navigation across sections 1 through 15, collapsible sidebars, direct field editing, dynamic row management for scenario-flow states and equipment, per-section locks, per-state locks inside scenario flow, and selective export controls for the generated Word document.

The authoritative domain model is defined in `src/lib/scenario-schema.ts` and `src/lib/types.ts`. Every scenario is represented as a strongly typed document containing course information, learning objectives, clinical setting, instructor and confederate roles, patient profile, scenario information, scenario flow, equipment, debrief details, simulator preparation, monitor setup, appendix images, and document metadata. The schema layer is important to the maintainability of the project because it serves as the contract between the UI, the server routes, the OpenAI structured output parser, and the DOCX export layer. Rather than accepting arbitrary model output, the application parses AI responses back into this schema and then normalizes the result before presenting it to the user.

AI scenario generation lives mainly in `src/lib/generation.ts`. The generation layer uses the OpenAI Responses API with structured parsing against Zod schemas, optional vector-store file search for knowledge grounding, and domain prompts that enforce SIMTAC section order, instructor-facing tone, DD/MM/YYYY date formatting, Singapore clinical context, and known SimMan monitor, sound, and capability constraints. Two primary workflows are supported: full-scenario generation and single-section fill. In worksheet-assist flows, the system merges generated content into the user draft by filling only missing values, and in unlocked-update flows it seeds blank versions of only the unlocked sections before asking the model to regenerate those areas.

Simulator compatibility is handled explicitly rather than left to prompt quality alone. `src/lib/simman-catalog.ts` provides allowed monitor layouts, monitor parameters, heart sounds, lung sounds, bowel sounds, and known SimMan capabilities. `src/lib/simman-validator.ts` then inspects generated or edited scenarios and returns warnings when unsupported monitor selections, excess waveform counts, invalid dates, misfiled SimMan tags, or unsupported simulator features are detected. This means the system behaves less like unconstrained text generation and more like a guarded domain authoring tool, where AI assistance is always mediated by schema and validation layers.

DOCX export is implemented in `src/lib/docx-export.ts` using the `docx` library. The export path preserves the worksheet structure as a Word document, renders sections 9 and 10 in landscape for readability, supports user selection of which scenario-flow columns should be included, and can embed saved appendix images directly into the exported file. The export route itself is simple, but the result is meant to be editable downstream, which makes the Word document a real working artifact rather than a view-only report.

## Knowledge and Document Processing

Knowledge retrieval is implemented through an OpenAI vector store rather than a local search index or database. The app expects an `OPENAI_VECTOR_STORE_ID` and, when configured, attaches file-search tools to scenario-generation requests so the model can ground outputs in uploaded or bootstrapped reference material. The bootstrap scripts in `scripts/bootstrap-vector-store.ts` and `scripts/ingest-reference-files.ts` seed the vector store from local SIMTAC-related resource files, and they can create a vector store automatically when one has not yet been provisioned.

Runtime knowledge administration is intentionally narrow. The upload route accepts `.docx`, `.pdf`, and `.txt` files, extracts raw text, normalizes whitespace, and re-uploads the content to OpenAI as plain text before attaching it to the vector store. The delete route removes both the vector-store file and the underlying OpenAI file when possible. Notably, the knowledge-library listing route currently returns `403` with the message that listing is disabled in the app, and there is no active UI for browsing the stored reference corpus. In operational terms, this means knowledge ingestion and deletion exist, but knowledge observability is still limited.

Document extraction lives in `src/lib/documents.ts`. For runtime uploads, the system supports `.docx`, `.pdf`, and `.txt`. For local ingestion scripts, it can also normalize `.doc`, `.xls`, `.xlsx`, and `.pptx` into text before upload. This gives the project a practical ingestion path for institutional reference material that may exist in inconsistent office-document formats, while keeping the generation layer itself text-based and model-friendly.

## State, Storage, and User Workflow

The application does not use a database for authored scenarios. Draft state is stored in browser `localStorage` under a stable application key, and the UI restores mode, prompt, scenario content, warnings, citations, sidebar state, image-generation settings, and some lock state on reload. This keeps the architecture lightweight and easy to deploy, but it also means scenario persistence is device- and browser-specific unless the user explicitly exports the result. There is no server-side draft history, collaboration model, or revision timeline in the current implementation.

Appendix image workflow is handled separately from the scenario text flow. Users can generate new images or refine existing ones through `POST /api/imagegen/generate`, and the server automatically prepends a Singapore healthcare context to the image prompt. Generated images can then be saved into the in-memory scenario draft and later embedded in the DOCX appendix. This is useful for scene-setting visuals such as ward or resuscitation-bay context, but the UI guidance explicitly warns against using it for imaging modalities such as X-rays or ECGs.

The AI-control model is intentionally simple in the UI. The user can select a `thinkingDepth` setting, but the interface currently clamps stored values to 0 through 2 even though the underlying schema supports 0 through 4. Model selection is not exposed in the UI and is resolved server-side from environment configuration, defaulting to `gpt-5.4-mini` for scenario generation and `gpt-image-1.5` for image workflows unless overridden in environment variables.

## Security and Access Control

The deployment is protected by a site-wide password gate enforced in `src/proxy.ts` and `src/lib/site-auth.ts`. All non-public routes require a cookie set by `POST /api/auth/login`, and API routes return `401` rather than redirect when site access has not been granted. This is a lightweight access model suitable for controlled pilots or internal deployments, but it is not a substitute for user identity, auditability, or role-based authorization.

Knowledge-administration routes use a separate `KNOWLEDGE_ADMIN_PASSCODE`, accepted either via the `x-admin-passcode` header or form/query input depending on route. Logging is routed through `src/lib/security.ts`, which redacts Singapore NRIC-style identifiers, email addresses, and phone numbers from error messages before logging. This is a meaningful privacy safeguard for a simulation-authoring context where prompts or uploaded files may contain realistic patient-like identifiers.

Rate limiting is implemented per route bucket in `src/lib/rate-limit.ts` and `src/lib/http.ts` using an in-memory map stored on the Node.js global object. This is sufficient for local development and simple single-instance deployments, but future maintainers should treat it as instance-local protection rather than a distributed rate-limiting solution. In horizontally scaled or serverless environments, rate limits will effectively be best-effort unless moved to a shared backing store.

## Deployment and Operations

Operationally, the project is designed for straightforward Next.js deployment, with Vercel explicitly documented as the target platform. Required configuration is concentrated in a small set of environment variables: `OPENAI_API_KEY`, `OPENAI_VECTOR_STORE_ID`, `KNOWLEDGE_ADMIN_PASSCODE`, and `SITE_ACCESS_PASSWORD`, with optional overrides for the text and image models. The API routes explicitly declare `runtime = "nodejs"` where they depend on SDK and file-processing behavior that should not run in the Edge runtime.

Because the system has no relational database, deployment complexity is low compared with most production web applications. There are no migrations, no session tables, no cache invalidation layer, and no queueing infrastructure. The principal external dependency is the OpenAI platform, specifically the responses, files, vector stores, and image endpoints. As a result, the most likely operational failures are missing environment variables, absent vector-store bootstrap, rejected or malformed uploads, model/API errors, or frontend browser storage issues rather than database or ORM problems.

The most important maintenance scripts are the vector-store bootstrap and extended reference-ingest scripts. These create or populate the retrieval corpus from institutional files in the local `Resources/` directory structure. Any future migration away from OpenAI-hosted retrieval would need to replace both these ingestion paths and the `file_search` tool attachment in generation requests.

## Testing and Verification

The repository includes a credible verification baseline for a project of this size. Unit tests cover schema handling, normalization, reasoning config, date handling, image context behavior, DOCX export, and other domain utilities. Integration tests exercise API route behavior such as DOCX export and the intentionally disabled knowledge-listing route. End-to-end Playwright coverage checks practical user flows including site unlock, creation-mode selection, worksheet editing, scenario-flow expansion and locking, equipment editing, modal workflows such as `Update Unlocked with AI`, and appendix-image preview behavior.

This testing strategy is important for handoff because the application’s risk is mostly in domain regression rather than raw algorithmic complexity. Breakage is most likely to appear as malformed worksheet content, incorrect lock preservation, export regressions, or UI workflow drift. The current suite is already oriented toward those failure modes. What it does not yet provide is deep operational observability, synthetic monitoring, or production telemetry.

## Usage Metrics and Observability

The current repository does not implement a persistent usage-metrics pipeline, analytics dashboard, or simulation-event warehouse. There is no database-backed record of generated scenarios, export counts, user sessions, or knowledge-upload history beyond what may exist externally in platform logs. In practice, operational visibility today comes from browser behavior, server logs, OpenAI-side object state, and the automated test suite rather than from product analytics.

If this project moves beyond a controlled pilot or internal tool phase, likely next-step infrastructure would include authenticated users, server-side scenario persistence, explicit audit logging for uploads and deletes, centralized rate limiting, knowledge-library inventory visibility, and analytics around scenario generation volume, export behavior, and failure rates. None of those are required to understand or maintain the current product, but they define the main expansion path.

## Handoff Considerations

The clearest strengths of the current codebase are its tight domain focus, explicit schema contracts, simulator-aware validation, simple deployment model, and practical authoring/export workflow. The clearest tradeoffs are equally deliberate: the main UI is concentrated in one large client component, drafts are only local unless exported, access control is password-based rather than identity-based, observability is limited, and some administrative capability such as knowledge listing exists only partially. A new engineering team could extend this system without rewriting it, but the first architectural decisions would likely revolve around whether the product should remain a lightweight single-workspace authoring tool or evolve into a multi-user platform with persistence, auditability, and richer operational controls.
